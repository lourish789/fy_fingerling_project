§0  /  Verdict

Where the paper stands

The results are sound and reproduce to the printed digit. The description of the system that produced them does not match the system in the repository, and the gap is wide enough that a reviewer with repository access would find it.

Verified

Detection metrics — Table 3

The checkpoint’s own stored metrics and an independent re-run reproduce P 0.811, R 0.782, mAP@0.5 0.821, mAP@0.5:0.95 0.479 and all three per-class rows. Differences ≤ 0.002 are rounding.

Verified

Every statistic — §3.3, §3.4, Table 5

Wilson intervals, paired t, Bland–Altman limits, Cochran–Armitage z, χ², the r = 0.943 correlation and the 3.5–4.6 % CVs all reproduce exactly.

Contradicted

Methods §2.5 — tracking, counting, logging

The tracker is not SORT. There is no Kalman filter, no IoU association, no direction gate and no majority vote, and the shipped configuration does not use the counting line at all.

Contradicted

Table 2 — configuration

Seven rows disagree with config/config.yaml or with the checkpoint’s stored train_args. The confidence-threshold row cites config.yaml explicitly and contradicts it.

Contradicted

Table 1 — dataset composition

332 images, not 330. The dataset is not balanced: 39.5 / 39.8 / 20.8 % by dominant class, 51.4 / 36.2 / 12.5 % by instance.

Unsupported

“No false positives or double counts”

Not supportable on the supplied footage, and structurally implausible: the training set contains zero background images, so the model has never been shown a negative example.

§3  /  Sample test on the supplied footage

111 fish in a clip that contains one

The shipped pipeline was replicated exactly — same weights, same FingerlingTracker class, parameters read from config/config.yaml — and run over every frame of VID_20260617_151857.mp4 (102 s, 2 815 frames) at stride 1. Every counted event was logged with its frame, track id, class and bounding box, then reviewed as an image crop.

VID_20260617_151857.mp4 · 2 815 frames · every frame processed

The same input, counted three ways.

As shipped
conf 0.15, unique_track 111 2 514 detections, 140 tracks. 57 juvenile, 47 fingerling, 7 post-fingerling.
As the manuscript describes it
conf 0.50, line crossing 3 206 detections, 49 tracks. All three labelled juvenile.
Fish actually in the clip
counted by eye 1–2 The channel is empty for most of the runtime and never holds more than two.

On the second video — effectively a negative control, with the channel empty almost throughout — the shipped configuration reports 49 fish and the manuscript’s configuration reports 0.

Of the 111 counted detections, a visual audit of every one finds 26 on an actual fish and 85 (77 %) on wet pavement, paving-slab joints, puddles and the outer wall of the pipe — background outside the channel entirely. The 26 true-fish detections are not 26 fish: they are the same one or two individuals, re-acquired under a new track id each time the fish leaves and re-enters the frame as the camera pans.

A nuance that matters for the fix

Raising the confidence threshold alone does not remove these. In the first video the two highest-confidence detections in the entire clip are fingerling 0.79 on a paving-slab joint and fingerling 0.80 on the shadow at the pipe’s cut edge — both well above 0.50. What suppresses them is the line-crossing requirement: static background never crosses the line, and a transiting fish does.

That is a mechanistic argument for the counting-line design the manuscript already describes, and it belongs in §4.2. Direction-gated line crossing is not merely a de-duplication device — it is the system’s only working defence against static background false positives.

What this does and does not show

It does not invalidate the 86.5 % figure. That came from controlled tank rounds with a fixed camera and the rig filling the frame; these videos are handheld, pan across unrelated background, and were evidently shot to document the apparatus. It does show three things worth acknowledging:

  1. The shipped configuration is not the validated configuration — 111 vs 3, and 49 vs 0, on identical input. Whatever produced Table 4, it was not the configuration in config.yaml.
  2. Out-of-channel background is a live failure mode, following directly from a training set with no negative examples. Any deployment where the camera sees anything but the channel over-counts badly.
  3. Track fragmentation causes double counting, contradicting the “no double counts” claim and partly offsetting the undercount — two errors of opposite sign that round-level totals cannot separate.
Recommended addition

Add a short §3.6, “Behaviour outside the validated envelope”, reporting exactly this. It reads as a strength: it shows the system was tested beyond the conditions that flattered it, it motivates recommendations (i) and (iv) far more concretely than the current text, and it pre-empts the first thing a reviewer with repository access would find.

§1  /  Contradicted by the code

Seventeen claims that do not survive contact with the repository

Each entry quotes the manuscript, gives the evidence, and proposes replacement text. None of them touch the results — they are all descriptions of how the results were obtained.

1.1Critical

The tracker is not SORT

§2.5

“detections are passed to the Simple Online and Realtime Tracking algorithm (SORT; Bewley et al., 2016), which assigns each fish a persistent identity using a Kalman filter for motion prediction and the Hungarian algorithm for intersection-over-union association.”

In src/models/tracker.py:

  • No Kalman filter exists anywhere in src/. filterpy is installed but never imported. Track.predict() is a two-point constant-velocity extrapolation: predicted = center + (history[-1] − history[-2]).
  • Association is by Euclidean centroid distance, not IoU. _compute_cost_matrix() builds a pixel-distance matrix; _compute_iou() is defined and never called; the iou_threshold = 0.3 constructor argument is stored and never read.
  • The gate that actually rejects matches is max_distance — 160 px in config.yaml.
  • Hungarian assignment via scipy.optimize.linear_sum_assignment is correct.
Suggested replacement

“Detections are associated frame-to-frame by a lightweight SORT-style tracker (after Bewley et al., 2016): Hungarian assignment on Euclidean centroid distance, with constant-velocity motion prediction and a fixed gating radius of 160 px. Unlike SORT proper it uses neither a Kalman filter nor IoU association; the simplification was acceptable because the observation geometry keeps fish separated and slow-moving.”

Table 2 loses the row “Association IoU 0.30” and gains “Gating radius 160 px (centroid distance)”.

1.2Critical

The counting line and direction gate are not what runs

§2.5 and Table 2

“Counting is performed by a virtual line drawn horizontally across the mid-frame at y = 0.50 … the count is incremented only when the centroid crosses the line in the downstream direction; upstream crossings are discarded.”

Three separate problems:

  1. config/config.yaml ships counting.mode: "unique_track". In that mode _setup_counting_line() never creates a line, the visualiser never draws one, and _count_unique_tracks() increments the total the moment a track reaches count_min_hits = 2 — anywhere in the frame, moving in any direction, or not moving at all.
  2. Even in line_crossing mode there is no direction gate. _check_line_crossings() fires on prev < line <= curr or prev > line >= curr — both directions. track.get_direction() is called but its return value is discarded. Re-counting is prevented by a one-shot counted flag, not by direction.
  3. Consequently “a fish that hesitates and re-crosses is not counted twice” holds for a single track — but when track identity is lost and re-acquired, which happens constantly on this footage, the fish is counted again under a new id.

This is the most consequential discrepancy in the paper; it is quantified in §3.

Two ways out — one is much better

Either change config.yaml to line_crossing and implement the direction gate, or change the manuscript to describe unique_track. The former is strongly preferable: the manuscript’s described method is the better one, and it is 37× closer to the truth on the supplied footage.

1.3Critical

Majority-vote class assignment does not exist

§2.5

“The class label attached to each counted fish … is the modal label over all frames in which the track retained its identity, a majority vote that absorbs isolated misclassified frames.”

Track.update() overwrites class_name with the current frame’s label on every update. The label recorded at count time is whichever class the most recent matched detection carried. A repository-wide search for most_common, Counter(, vote or majority in src/ returns nothing.

This matters because size sorting is the class assignment: with per-frame overwriting, a fish whose class flickers is sorted by a coin flip on its last frame. In the video run the same physical juvenile was recorded under all three class labels at different moments.

Fix

Implement the vote — about eight lines: keep a Counter on Track, update it in update(), read its mode when counting. Otherwise remove the claim.

1.5Critical

“All errors were undercounts; no false positives or double counts”

Stated in the Table 4 footnote, restated in the abstract (“Every error was an undercount”) and in §3.4. Three independent lines of evidence contradict it at the shipped configuration:

  • On the supplied video. 85 of 111 counted detections are on background — see §3.
  • On the held-out validation images. At the shipped conf 0.15 the detector predicts 197 boxes against 157 true instances (125.5 %) — a net overcount. It becomes net-unbiased only near conf 0.50 (151/157 = 96.2 %).
  • Double counts are structural. Track identity is lost and re-acquired repeatedly, so the 26 true-fish detections correspond to at most two individuals.
Root cause — the most actionable finding in this review

The dataset contains zero background images. All 332 images in all three splits carry at least one annotated fish; there are no empty label files, and Ultralytics reports 0 backgrounds on every split. The model was never shown a negative example, so it has no representation of “not a fish”. Ultralytics’ own guidance is 0–10 % background images; at 332 images that is 20–35 negatives.

Photograph 30–50 frames of the empty rig, the surrounding pavement, wet ground and the pipe exterior; add them with empty label files; retrain. It is cheap and it is the highest-return change available.

Narrow the claim to what the data support

“Within the 156 scored passages, every discrepancy from the reference was an undercount. False positives were not observed under the controlled tank conditions of the validation rounds; §4.4 reports their appearance outside that envelope.”

1.6Fix text + code

The CSV log does not contain what is claimed

§2.5

“Each counted fish is written to a CSV log with a timestamp, class label and track identifier, which permits complete post-hoc reconstruction of any round.”

CSVLogger writes a per-frame snapshot, not a per-fish event: timestamp, frame, total, fingerling, post_fingerling, juvenile, unknown, fps. There is no track-identifier column and no per-fish row. Per-fish reconstruction is impossible, and the “auditability through the CSV log” argument in §4.3 rests on a capability the code does not have.

Also a genuine bug. The header is written with an escaped \\n inside a non-raw f-string, so a literal backslash-n is emitted instead of a newline and the header runs into the first data row. Visible in output/counts.csv:

timestamp,frame,total,fingerling,post_fingerling,juvenile,unknown,fps\n2026-05-12T11:31:02.248819,30,9,...
Fix

src/streaming/server.py:738 — write fps\n, not fps\\n. Adding a real per-fish event log is roughly ten lines and would make the §4.3 claim true.

FingerlingDetector.detect() calls _preprocess() by default, applying CLAHE (clipLimit 2.0, 8×8 tiles) in LAB space to every frame before inference. FingerlingCounter calls detect(frame) with the default, so CLAHE is always on in production. The model was trained without it and Table 3 was computed without it.

1.9Critical

The augmentation list is not what was applied

§2.3

“Eight augmentations were applied to the training partition only — horizontal and vertical flip, ±15° rotation, ±25 % brightness, ±15 % exposure, Gaussian blur to 2.5 px, mosaic and cutout”

  • The exported dataset contains 232 training images = exactly 70 % of the 332 source images. Roboflow offline augmentation would have multiplied that (3× → 696). No augmented copies were exported, so these were not Roboflow-baked augmentations.
  • What was actually applied, from the checkpoint, are the Ultralytics on-the-fly defaults: hsv_h 0.015, hsv_s 0.7, hsv_v 0.4, translate 0.1, scale 0.5, fliplr 0.5, mosaic 1.0, erasing 0.4, close_mosaic 10.
  • Critically, degrees: 0.0 (no rotation) and flipud: 0.0 (no vertical flip) — two of the eight listed augmentations were not applied, and neither was Gaussian blur.

Replace the list with the checkpoint values. Since fish appear at any orientation in the channel, the absence of rotation and vertical flip is also a concrete improvement lead for §5(ii).

1.12Fix text

The observation window is not glazed

§2.2

“A section of the pipe was opened and glazed to form a transparent observation window.”

The supplied footage shows a PVC pipe with a rectangular window cut in the top and no glazing — an open channel viewed from directly above, water surface exposed to air. This is what the Fig. 1 caption already says (“open-channel observation cross-section”), so §2.2 contradicts the figure it cites.

1.13Fix equation

Equation (4) uses the wrong cross-section

Eq. (4) A = bh = 0.10 × 0.05 = 0.005 m² is the area of a rectangular channel. The footage shows a round pipe with the top cut away, so the wetted section is a circular segment. For a 100 mm ID pipe at 50 mm depth, A = πr²/2 = 0.00393 m² — b·h overstates the true flow area by 27 %.

Either state that the observation section is a rectangular flume (and show it in Fig. 1 Detail A), or replace Eq. (4) with the circular-segment form A = r²(θ − sin θ)/2, θ = 2 arccos((r − h)/r).

Equations (1)–(3) are all arithmetically correct: 10.0 L, 13.25 L, 2452.5 Pa.

1.14Critical

The flow rate is inconsistent with the stated head

§2.6 and §2.2 Eq. (3)

“continuous flow at approximately 0.5 L min⁻¹” · “2.45 kPa … sufficient for a gentle gravity discharge”

  • Free gravity discharge at H = 0.25 m gives v = √(2gH) = 2.21 m s⁻¹. Through even a 20 mm pipe (Cd 0.62) that is ≈ 26 L min⁻¹; through a 100 mm pipe, ≈ 650 L min⁻¹. 0.5 L min⁻¹ is two to three orders of magnitude lower, so the flow must have been throttled — by a valve or part-open tap the Methods does not mention. Add it; it is part of the reproducible protocol.
  • At 0.5 L min⁻¹ over A = 0.005 m² the mean velocity is 1.7 mm s⁻¹, and moving 10 L takes 20 minutes — inconsistent with “a population typically cleared within five to eight minutes” and with the ten-minute round ceiling.
  • More seriously, 1.7 mm s⁻¹ is far below any velocity that would produce the strong station-holding rheotaxis described in §3.1 — the paper’s headline behavioural finding. Either the figure is a typo (5 L min⁻¹ gives 17 mm s⁻¹ and a two-minute transfer, which fits the narrative), or the relevant velocity is the local one at the constricted pipe inlet rather than the channel mean.

Re-check the number, say how it was measured (timed volume? rotameter?), and if the rheotaxis argument depends on velocity, report the velocity at the point the fish experienced it.

2.3Add a sentence

One methodological note on the Wilson interval

The Wilson interval on 135/156 treats the passages as 156 independent Bernoulli trials. They are not: the same 20 / 18 / 14 individuals were re-used across the three rounds of their class, and fish within a round share water, light, clustering and operator state. The effective independent unit is closer to nine rounds (or 52 fish) than 156 trials — a pseudoreplication concern for generalisation.

Reassuringly, it does not inflate the reported precision. A cluster bootstrap resampling the nine rounds (200 000 draws) gives 84.1 – 89.2 %, narrower than the Wilson interval, because between-round variance is small (round accuracies 85.0, 80.0, 85.0, 88.9, 83.3, 88.9, 92.9, 85.7, 92.9; SD 4.3 pp).

Suggested addition to §2.8 or §4.4

“The Wilson interval treats the 156 passages as independent; because the same individuals were re-used across rounds, the effective independent sample is the nine rounds. A cluster bootstrap over rounds gives 84.1–89.2 %, so the reported interval is conservative rather than optimistic, but generalisation is limited by the nine rounds, not by the 156 passages.”

Also verified: Equations (1)–(3) exact; Flask on TCP port 5000; class names and label mapping consistent end-to-end (COCO ids 1/2/3 → YOLO 0/1/2 → {0: fingerling, 1: post_fingerling, 2: juvenile}, instance counts matching on both sides — no off-by-one in the remap); YOLOv8n, 100 epochs, batch 16, 640 × 640, weight decay 5 × 10⁻⁴; validation partition 66 images / 157 instances.

The test result is slightly better than validation — the model is not overfitted to the selection split. This converts “mAP@0.5 = 0.822 on validation” into a defensible generalisation claim.

4.3Add

Runtime, deployability and backend parity

The throughput table in §1.15 belongs in §4.3, where the paper compares against commercial counters on cost. Throughput is the other axis on which that comparison should be made: 5–8 FPS on CPU against a commercial channel counter’s continuous operation is a real limitation the cost argument currently obscures.

Backend parity. PyTorch vs ONNX Runtime, CLAHE on both sides, 66 validation images: 233 vs 224 detections (−3.9 %), 18 of 66 images differ, max per-image difference 2. Worth one sentence in §2.5 or a declaration under Data and Code Availability, since the deployed artefact is the ONNX one.
